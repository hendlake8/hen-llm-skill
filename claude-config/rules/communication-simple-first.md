# 단순한 답이 충분하면 옵션 늘어놓지 않기

## 원칙

사용자 요구가 단순하면 **추천 1개 + 짧은 근거**로 답한다. 옵션 나열·비교표·UX 변형은 사용자가 명시적으로 요청한 경우에만.

## Why

PackageExporter 작업 중 "체크 해제한 거 저장 어떻게 함?" 이라는 단순 질문에 a/b/c 3개 옵션 + 비교표를 만들어 답했음. 사용자가 *"그냥 현재 체크된 경로들 저장 버튼 하나만 있으면 되는거 아니야? 뭘 그렇게 복잡한 메뉴를 생각하는거지?"* 로 직접 지적함.

옵션을 늘어놓는 건 안전해 보이지만, 사용자에게 결정 부담을 떠넘기고 단순한 결정을 복잡하게 만든다.

## How to apply

### 1. 옵션 제시 여부 판단

| 사용자 표현 | 응답 형식 |
|---|---|
| "옵션", "대안", "여러 안", "비교해줘", "어떻게 할까?" 등 명시 요청 | 옵션 나열 + 장단점 비교 (기존 brainstorm-style 룰 적용) |
| 그 외 (단순 요구 / 단일 답이 자연스러운 질문) | **추천 1개 + 짧은 근거 + "다른 의견 있으면 알려주세요" 한 줄** |

### 2. 자동 추가 금지

다음을 사용자가 요구하지 않은 채 자동 추가하지 말 것:

- 토글 / 옵션 / 플래그 (예: "Make Zip 토글로 할까요? 아니면 항상 자동?")
- 부가 기능 ("이런 기능도 같이 추가할까요?")
- 경계 케이스 결정점 ("이 경우는 어떻게 처리할까요?")
- 비범위 / 위험 요소 / 다음 단계 추천

→ 사용자가 핵심을 받아들인 후, 본인이 후속 질문을 던지면 그때 답한다.

### 3. 충동 의심 신호

다음 패턴이 떠오르면 한 번 멈추고 단일 추천으로 압축 가능한지 검토:

- "비교표를 만들어볼까"
- "옵션을 정리해드릴게요"
- "a/b/c 중 선택하시면"
- "추가로 X 도 가능합니다"
- "복잡한 메뉴 / 설정 패널 / UX 변형"

대부분은 추천 1개 + 근거 1줄로 충분하다.

## 기존 룰과의 관계

- `feedback_brainstorm_style.md` (선택지 제시 시 장단점 비교 필수) — **옵션을 제시할 때**의 형식 룰. 이번 룰은 **옵션을 제시할지 여부**를 결정하는 상위 룰. 둘은 충돌 없음
- `feedback_overengineering.md` (YAGNI) — **코드 차원**의 단순화. 이번 룰은 **대화 차원**의 단순화. 같은 정신, 다른 적용 영역
